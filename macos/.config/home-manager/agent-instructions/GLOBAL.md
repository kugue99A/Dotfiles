## 1. エンジニアリングの柱：関数型プログラミングと関数型ドメインモデリング

関数型プログラミング（FP）と関数型ドメインモデリング（FDM）は、私のエンジニアリングで **最も中心にある概念** である。

私の仕事は、抽象的な問題を捉え、それを具体的な実装に落とし込むことの繰り返しである。設計、実装、レビュー、リファクタリング、ドキュメント、チケット化のどれでも、言語やレイヤー（サーバー、クライアントの状態や画面、インフラ、テスト）を問わず、まずこの考え方で問題を捉え、この考え方で具体に落とし込むこと。

### 1.1 判断の優先順位

**意味論的な正しさ ＞ 関数型としての正しさ ＞ 長期的な保守性 ＞ 実装工数**

工数の大小を理由に、意味の曖昧なモデル（フラグの組み合わせ、文字列による状態、`null` の多用）を選ばない。

### 1.3 抽象から具体へ落とし込む手順

1. **言葉にする**: ドメインの名詞と動詞を、ユビキタス言語として書き出す。コード上の名前は、その言葉と一致させる。
2. **型で表す**: 「A かつ B」は直積型（レコード・構造体）、「A または B」は直和型（判別共用体・`enum`）で表す。プリミティブ型は使わず、意味のある型（newtype・branded type）にする。
3. **不正な状態を表現できなくする**: スマートコンストラクタで作るときに検証する（バリデーションではなくパースする）。フラグや並列の optional は、直和型に置き換える。状態遷移は、状態ごとの型と遷移関数で表す。
4. **ワークフローを関数にする**: `入力 → Result<出力（イベント）, ドメインエラー>` の型をまず書き、小さな関数の合成として実装する。
5. **純粋なコアと I/O の殻に分ける**: 「読む → 決める（純粋）→ 書く」の順にする。ドメインのコードは I/O、時計、乱数、グローバルな状態に触れない。これらは引数（関数や値）として外から渡す。
6. **境界で変換する**: ドメインの型は直接シリアライズしない。DTO との変換を明示的に書く。外部からの入力は、境界で必ずパースしてドメインの型にする。
7. **進化させる**: 型を変えたら、網羅的な `match` / `switch` によって影響箇所をコンパイラに列挙させる。

### 1.4 守ること

- 純粋関数と不変データを基本にする。破壊的な変更は、局所的で外から観測できない場合に限る。
- 全域関数にし、エラーは値（`Result` / `Either`）として返す。ドメインのコードでは `throw`、`panic!`、`unwrap` を使わない。
- 網羅的なパターンマッチを使う。新しいケースを隠す `_` / `default` は使わない。TypeScript では `assertNever` を使う。
- 依存は、関数やインターフェースを引数で渡して注入する。サービスロケーターや、隠れたシングルトンは使わない。
- コマンドとクエリを分ける（CQS）。更新して同時に値を返すような、曖昧な API を作らない。
- 継承ではなく合成を使う。クラス階層ではなく、直和型と関数で表す。
- 副作用は型か関数のシグネチャに現れるようにし、隠さない。
- **UI もドメインとして扱う**:
  - 画面の状態は、`loading` / `failure` / `empty` / `success` のような直和型で表す。真偽値の組み合わせにしない。
  - フォームは、入力値をドメインの型にするパース関数を通す。
  - 画面遷移や画面の外枠も型で宣言する。

### 1.5 言語ごとの落とし込み

- **TypeScript**:
  - `strict` を前提にする。
  - 判別共用体と `assertNever` を使う。
  - branded type をスマートコンストラクタで作る。
  - `Result` 型を使い、`as` によるキャストや `any` は使わない。
  - 外部入力は境界でパースする（zod などのスキーマ）。
- **Rust**:
  - フィールドを非公開にした newtype と、`TryFrom` / `parse` のコンストラクタを使う。
  - 状態は `enum` で表し、エラーは `Result` と `thiserror` で表す。
  - ドメイン層は I/O や非同期処理に依存させない。
- **Swift / Kotlin**: `enum`（関連値付き）や `sealed` 型、値型、`Result` を使う。
- **それ以外の言語**: その言語で最も近い表現（タグ付きの共用体、型ヒント付きの不変データクラスなど）を選び、同じ原則を守る。

### 1.6 リポジトリとの関係

- リポジトリに FP や FDM の規約（例：`docs/FUNCTIONAL_DOMAIN_MODELING.md`）がある場合は、具体的な点についてそちらを優先する。この節は、そうした規約の上位にある原則である。
- 規約のないリポジトリでも、この原則で設計する。既存のコードが原則から外れている場合は、触る範囲で目標の形に近づける。大きな乖離はチケットとして提案する。

## 2. モバイル UI の原則（私が作るプロダクト共通）

- **画面の上は読むところ、下は触るところ。**
  - 操作（ボタン、戻る・閉じる、画面遷移、タブ、検索欄、送信・取消・削除、確認）は、画面の下半分に集める。
  - 左上の「戻る」や右上の「閉じる」など、上の隅に置く操作は明確なアンチパターンとして扱う。
  - 画面の上側は、情報の表示（タイトル、日付、状態、通知）に使う。
- 確認は、画面中央のダイアログではなくボトムシートで出す。フォームの送信ボタンは、下部に固定する。
- ボタン類には、iOS の Liquid Glass（グラスモーフィズム）を適用する。使えない環境（Android、Web、「透明度を下げる」がオン）では、不透明な表示に切り替える。
- ジェスチャーの方向には、一つの意味だけを持たせる（例：縦は時間の移動、横は見え方の切替）。独自のジェスチャーで行う操作は、必ずボタンでもできるようにする。
